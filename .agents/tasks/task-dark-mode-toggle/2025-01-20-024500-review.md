# Dark mode toggle via CSS custom properties

This change introduces a light/dark theme toggle to the Saga Bus Navigator PWA. The approach uses CSS custom properties defined on `:root` and overridden via a `[data-theme="dark"]` selector on `<html>`, managed by a `ThemeManager` class that persists the choice in `localStorage` and falls back to `prefers-color-scheme`. Existing hardcoded colors in `app.css`, `timetable.css`, and `footer-pages.css` are replaced with variable references, and the pre-existing calendar modal `@media (prefers-color-scheme: dark)` block is migrated to the `[data-theme="dark"]` selector.

**Watch for:** Flash of light-mode content on dark-preference users (confirmed) due to theme script running only at DOMContentLoaded; incomplete variable migration leaves several hardcoded colors in `footer-pages.css` that won't respond to dark mode (confirmed); `meta[name="theme-color"]` stays static so the browser chrome won't match the selected theme (confirmed).

## High-level view

A flash-of-unstyled-content (FOUC) gap exists because `theme.js` defers initialization until `DOMContentLoaded`. For any user with a persisted dark-mode preference or a dark OS setting, the page will render fully in light mode, then snap to dark once the script runs. The fix is a synchronous inline `<script>` in `<head>` that sets the `data-theme` attribute before first paint.

The variable migration covers the main structural elements but leaves several selectors in `footer-pages.css` using hardcoded accent and background colors. These elements will remain light-themed even when dark mode is active, creating visual inconsistency in the footer modals.

The PWA `theme-color` meta tag is hardcoded to `#0066cc` and never updated when the theme changes. On mobile, the browser address bar and task-switcher color will mismatch dark mode.

## FOUC: theme script defers until DOMContentLoaded

`theme.js` is loaded as a regular `<script>` at the bottom of `<body>` and attaches its logic to `DOMContentLoaded`. The `<html>` element has no `data-theme` attribute in the static markup, so CSS renders with `:root` (light) values until JavaScript executes. On a slow connection or when the parser is busy evaluating other scripts, users with dark preference will see a full white flash before the theme flips.

The standard mitigation is a tiny inline script in `<head>`, immediately after the stylesheet links:

```html
<script>
(function() {
  var t = localStorage.getItem('theme');
  if (!t) t = matchMedia('(prefers-color-scheme: dark)').matches ? 'dark' : 'light';
  document.documentElement.setAttribute('data-theme', t);
})();
</script>
```

This runs synchronously before the browser paints, so the custom properties resolve correctly on first render. The `ThemeManager` class still initializes later and takes over state management; the inline script just prevents the visual flash.

## Incomplete variable migration in footer-pages.css

The diff converts overlay backgrounds, modal content, headers, and tab active states to CSS variables but leaves behind several selectors:

- `.footer-modal-title` keeps `color: #0066cc` (should be `var(--color-accent)`)
- `.footer-modal-close` keeps `color: #666` (should be `var(--color-text-secondary)`)
- `.footer-modal-close:hover` keeps `background-color: #f5f5f5; color: #333` (should be `var(--color-bg-primary)` and `var(--color-text-primary)`)
- `.footer-modal-close:focus-visible` keeps `outline: 3px solid #0066cc` (should use `var(--color-accent)`)
- `.footer-tab-button:hover` keeps `background-color: #e9ecef` (no matching variable; needs a new variable or use `var(--color-bg-primary)`)

These elements will render in their light-mode colors regardless of the active theme.

## Static PWA theme-color

The `<meta name="theme-color" content="#0066cc">` in `<head>` controls the browser address bar color on Android and the window title bar on some desktop browsers. When dark mode is active, the header gradient shifts to `#0a3d91`/`#072a66`, but the browser chrome stays bright blue.

`applyTheme()` should update this meta tag:

```js
const meta = document.querySelector('meta[name="theme-color"]');
if (meta) {
  meta.setAttribute('content',
    this.currentTheme === 'dark' ? '#0a3d91' : '#0066cc');
}
```

## Calendar modal: hardcoded dark palette diverges from variables

The migrated `[data-theme="dark"] .calendar-*` rules use their own one-off hex values (`#2c2c2c`, `#444`, `#3c3c3c`, etc.) instead of referencing the shared custom properties (`--color-bg-secondary`, `--color-border`, etc.). Future palette adjustments require updating both the variable block and the calendar overrides separately, and the calendar modal's dark palette visually diverges from the rest of the app (modal background is `#2c2c2c` while the app-wide secondary background is `#16213e`).

## No "reset to system" path

The `isUserSet` flag lives only in memory and is derived from whether localStorage contains a value. Once a user toggles the theme, the only way to return to OS-tracking behavior is to clear localStorage externally — there's no UI affordance for "use system preference." Worth noting for a follow-up iteration.

## Test coverage gaps

**Not tested:** the `DOMContentLoaded` auto-initialization path at the bottom of `theme.js`; behavior when the toggle button is missing from the DOM (the code handles it with null checks, but no test asserts that path); behavior with invalid localStorage values (e.g., `localStorage.setItem('theme', 'invalid')` — currently falls through to the OS-preference branch, which is correct but unverified).
